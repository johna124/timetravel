QUICK START
==============================================================================
Compile:
./compile.sh test      # Fast KDF for tests (~100x faster crypto tests)
./compile.sh release   # Full security for production (default if no arg provided in older versions, now required)

Watch a single directory (starts the monolith):
./build/timetravel start /path/to/project

or watch a single file (v1.6):
./build/timetravel start /path/to/project/file.c

or multiple targets at start:
./build/timetravel start src/ bin/ main.c

Add MORE repositories/files hot to the same daemon:
./build/timetravel add /path/to/another/project
./build/timetravel add /path/to/docs/readme.md

See the whole swarm from ANY directory:
./build/timetravel status

Edit files normally. To undo:
./build/timetravel undo /path/to/file.c --last --repo /path/to/project
./build/timetravel undo /path/to/file.c --to "2026-09-13 00:07:08" --repo /path/to/project
./build/timetravel undo /path/to/file.c --to "10 minutes ago" --repo /path/to/project
./build/timetravel undo /path/to/project --tag before-refactor --force --repo /path/to/project

To compare versions:
./build/timetravel diff /path/to/file.c --repo /path/to/project
./build/timetravel diff /path/to/file.c --to prev --repo /path/to/project
./build/timetravel diff /path/to/file.c --to 15 --repo /path/to/project

# To see inter-revision deltas, use dump --with-diff instead.
To view history and status:
./build/timetravel log /path/to/file.c --repo /path/to/project
./build/timetravel extlog /path/to/file.c --repo /path/to/project  # New in v1.6
./build/timetravel status --repo /path/to/project
./build/timetravel tag release-v1.0 --repo /path/to/project

To export all versions and diffs:
./build/timetravel dump /path/to/file.c --repo /path/to/project \
--out /tmp/tt_dump --with-diff

Lifecycle and maintenance:
./build/timetravel stop                    # stop the whole monolith
./build/timetravel stop --repo <dir>       # remove ONLY that repo
./build/timetravel restart <dir>
./build/timetravel tags [--repo <dir>]
./build/timetravel compact [--repo <dir>]  # manual (no more 03:00 auto-run)

Create an encrypted repository:
./build/timetravel start /path/to/project --encrypt

This prompts for a passphrase twice and creates:
/path/to/project/.timetravel/crypto.meta

Verify repository integrity:
./build/timetravel verify --repo /path/to/project

Compact a repository and run dedup GC:
./build/timetravel compact --repo /path/to/project

For encrypted repositories, compact/undo/verify may request the passphrase.

Run regression tests:
./compile.sh test
./mega_test.sh ./build/timetravel

Run sanitizer and concurrency audits:
# AddressSanitizer + UndefinedBehaviorSanitizer
./compile_asan.sh
./mega_test.sh ./build_san/timetravel

# ThreadSanitizer
./compile_tsan.sh
TSAN_OPTIONS="halt_on_error=1:second_deadlock_stack=1" \
./mega_test.sh ./build_tsan/timetravel

Important:
- Do not combine Valgrind with ASan or TSan.
- Do not combine ASan with TSan.
- When mega_test detects a TSan build, it automatically skips the Valgrind
memory audit section.
- Sanitizer builds are audit builds, not the production static binary.

1. WHAT IS TIME-TRAVEL
==============================================================================
Time-Travel is a real-time file versioning daemon that watches a directory
tree or individual files via inotify and records every change as compact
xdelta3 deltas.

Think of it as "Ctrl+Z for your entire project folder":

Core capture and restoration:
- Every edit, creation, and deletion is captured automatically.
- Restore any file or entire directory to any previous point in time.
- Named checkpoints (tags) for semantic rollback points.
- Diff between any two versions of a file.
- Full export of reconstructed versions and consecutive diffs.
- Atomic writes: restorations never leave corrupted files.
- No initial backup: only changes are recorded (copy-on-first-change).
- Per-file directory undo: each file reverts to its own previous version.

Multi-repo monolith (v1.3):
- ONE daemon watches up to 16 repositories at once.
- Hot add/remove of repositories without restarting.
- Global status across the whole swarm from any directory.
- Per-repo isolation: corruption in one repo never affects the others.

File Repos (v1.6):
- Watch individual files instead of entire directories.
- Perfect for config files, single scripts, or isolated modules.
- Shares the same daemon and store infrastructure as directory repos.

Dedup and encryption (v1.4):
- Files >= 1 MiB are stored as 64 KiB BLAKE2b content-addressed blocks,
shared across files and versions.
- Optional per-repository XChaCha20-Poly1305 encryption (AEAD).
- PBKDF2-HMAC-BLAKE2b key derivation; the passphrase is never stored.
- Store verification: detect corrupted or tampered .ttd files, invalid
magic, missing blocks, and failed AEAD authentication.
- Atomic compaction with fail-closed orphan-block GC.

Reliability and hygiene:
- Robust exclusions: .git, node_modules, __pycache__, target, .cache.
- Enhanced status showing daemon state, CPU, RAM, records, and bytes.
- Self-cleaning test battery: 170 assertions across 51 sections.
- Audited with ASan/UBSan, ThreadSanitizer and Valgrind (0 leaks).

The final CLI binary is static, approximately 274 KB (includes statically
compiled xdelta3, BLAKE2b, and the XChaCha20-Poly1305 crypto core), with
zero external runtime dependencies.

==============================================================================
2.1 THE MULTI-REPO MONOLITH
==============================================================================
v1.3 replaces the single-repo daemon with a monolith that owns an array of
repositories (up to TT_MAX_REPOS = 16). Each repository is an autonomous
unit with its own watched root, its own .timetravel store, its own in-memory
cache, its own debounce queue, and its own store writer.

TtDaemon (the monolith)
|- shared inotify fd (one for ALL repos)
|- shared timer fd (tick)
|- IPC socket fd (hot add/remove)
|- watch map:  inotify wd  ->  repo id   (event routing)
|- repos[0..TT_MAX_REPOS-1]:
TtLocalRepo
|- root / store_dir (.timetravel)
|- TtStateCache    (per-repo in-memory cache)
|- TtDebounce      (per-repo coalescing queue)
|- store writer    (per-repo .ttd)

Key properties:
- A single inotify instance serves every repo. Each watch descriptor is
mapped back to its repo, so an event in repo A is never recorded in B.

- Repos are added/removed at runtime over a Unix domain socket
(.timetravel/timetravel.ipc). A per-user registry under
/tmp/timetravel-<uid>/ provides global discovery (socket path, pid, and a
global status snapshot) so any CLI instance can find the monolith.

- Concurrency safety at startup is guaranteed by a boot lock (flock) plus
IPC discovery: whichever invocation wins the lock becomes the daemon, and
every other concurrent invocation detects it and joins as a client.

3. ON-DISK STORE STRUCTURE
==============================================================================
Each watched repository keeps its OWN independent store:

<repo>/.timetravel/
*.ttd                Binary record files (rotation at 64 MB)
tags                 Tag definitions (name\ttimestamp)
timetravel.pid       Daemon PID + startup timestamp
timetravel.status    Daemon state snapshot
repos.list           Hot-added repos, re-adopted on restart (v1.3)
timetravel.ipc       Unix socket for hot add/remove (v1.3)
crypto.meta          v1.4: present only in encrypted repositories
blocks/              v1.4: dedup block pool
xx/
yyyyy...     BLAKE2b-named 64 KiB blocks

4. BINARY FORMAT
==============================================================================
Compatibility: TTDLTA01. Everything little-endian.
Magic:     TTDLTA01  (8 bytes)
Version:   1         (4 bytes, uint32 little-endian)

Record format (packed, little-endian):
Offset  Size    Field
------  ------  -----
0       8       timestamp_ns   (uint64)
8       1       event_type     (uint8: CREATE=1, MODIFY=2, DELETE=3)
9       4       path_len       (uint32)
13      4       delta_size     (uint32)
17      8       file_size      (uint64)
25      var     path           (path_len bytes, no NUL)
25+pl   var     payload        (delta_size bytes)

Total record size: 25 + path_len + delta_size bytes.
Event types:
TT_EV_CREATE        = 1   Full content
TT_EV_MODIFY        = 2   xdelta3 delta against previous version
TT_EV_DELETE        = 3   Deleted file (no payload)
TT_EV_RENAME        = 4   Reserved
TT_EV_CREATE_DEDUP  = 5   v1.4: content stored as dedup block hashes

Encryption (v1.4):
When repository encryption is enabled, record payloads are stored as:
nonce(24) || ciphertext(delta_size) || tag(16)

The on-disk delta_size field contains the STORED size, i.e. plaintext
size + 24-byte nonce + 16-byte tag.

The reader decrypts the payload and reports the original plaintext size.

Record headers and paths are included in the AEAD AAD. They are
authenticated but NOT encrypted. Therefore, timestamps, paths and file
sizes remain visible in encrypted repositories.

==============================================================================
5. DELTA ENCODING WITH XDELTA3
==============================================================================
When a file changes, the engine attempts to encode the difference as an
xdelta3 delta against the previous cached version.

Conditions to produce a MODIFY record (delta):
1. The file has a previous version in cache (anchored=1).
2. The new content differs from the cached content.
3. The delta size is strictly less than the new file size.

If the delta is greater than or equal to the new file size (common with
very small files), a full CREATE record is written instead. This is correct
behavior: the restoration logic handles both CREATE and MODIFY.

Measured savings:
A 600-byte file with a 20-byte addition produces a ~30-byte delta. Without
delta encoding, the full 620 bytes would be stored. Savings factor: ~20x.

Thresholds:
TT_MAX_CAPTURE_SIZE    64 MB    Larger files are ignored.
Delta fallback         None     Automatic: delta >= new -> CREATE.

==============================================================================
6. CAPTURE MODEL (COPY-ON-FIRST-CHANGE)
==============================================================================
Time-Travel DOES NOT create an initial backup/snapshot on startup. This was
a deliberate design decision to avoid writing records for files that never
change.

How it works:
1. On daemon startup (or when a repo is added), all existing files are read
into a per-repo in-memory cache (TtStateCache). Each entry is marked as
baseline_pending=1 (no history) or anchored=0 (has history from previous
sessions).

2. NO records are written on startup. Zero.

3. When a file is modified for the first time:
- If baseline_pending: writes CREATE [original] (backdated to daemon
startup) + MODIFY/CREATE for the new content.
- If anchored but content differs from store: writes CREATE (reanchor)
for the new content.
- If anchored and content matches: writes MODIFY (delta).

4. Subsequent changes produce MODIFY (delta) or CREATE (fallback).
Why backdate CREATE [original] to daemon startup?
So that undo --tag or undo --to with a timestamp between startup and the
first change can find the original content. Without this backdating, the
original would have a timestamp later than the tag, making it invisible
for temporal restoration.

Recovery after daemon restart:
- Files with history in store: cached with anchored=0. First change triggers
reanchor (CREATE with full content).
- Files without history: cached with baseline_pending=1. First change writes

CREATE [original] + new version.
- The per-repo start timestamp is reset to current time on every adoption.

7.1 DAEMON LIFECYCLE (MULTI-REPO)
==============================================================================
start <dir|file>       
Start the monolith with <dir|file> as repo #0.
If a monolith is ALREADY running, <dir|file> is added
to it via IPC instead of starting a second daemon.

start <path> [path2] [path3] ... (max 10)
Start the monolith with one or more paths as repos.
Each path can be a file or directory.
If a monolith is ALREADY running, paths are added via IPC.
    
Examples:
timetravel start src/
timetravel start file.c

timetravel start *.c              # shell expands globs
timetravel start src/*.c          # shell expands globs

add <dir|file>         
Hot-add <dir|file> to the running monolith via IPC.
If no monolith is running, bootstraps one (same
as start). Safe to call concurrently: a boot lock
guarantees only ONE daemon is ever created.

stop                   
Stop the whole monolith (all repos).
stop --repo <dir>      Remove ONLY <dir> from the monolith (selective).
The daemon exits only when the last repo is removed.

restart <dir>          
Stop + start.
watch <dir> [-f]       Watch in foreground (-f) or background (default).

Concurrency guarantees (v1.3):
- Parallel `start`/`add` are serialized by a flock boot lock; exactly one
daemon is created and the rest join it as IPC clients.
- A repo that overlaps an already-watched repo (ancestor or descendant) is
rejected with an error.

==============================================================================
7.5 MAINTENANCE
==============================================================================
verify [--repo <dir>]
Verify repository integrity in read-only mode.

Checks performed:
- TTDLTA01 magic is validated on all .ttd files before reading records.
- Records are read and grouped by path.
- Per-path event chains are verified.
- TT_EV_CREATE: payload size must match file_size.
- TT_EV_CREATE_DEDUP: every referenced dedup block must exist, have the
expected size, and its BLAKE2b-256 hash must match the reference.
- TT_EV_MODIFY: the xdelta3 delta must decode against the reconstructed
previous state.
- TT_EV_DELETE: clears the reconstruction state for that path.
- Encrypted repositories: AEAD authentication is enforced.

Returns 0 when the store is clean.
Returns non-zero when corruption, tampering, missing dedup blocks, invalid
magic, or authentication failure is detected.
compact [--repo <dir>]

Collapse delta chains and rewrite the store atomically.

In v1.4, compact also runs dedup GC:
orphan blocks not referenced by any record are removed.

For encrypted repositories, compact requires the correct passphrase.
If the repository cannot be read/authenticated, compact aborts and
GC does not delete blocks.

start <dir> --encrypt
Create a new encrypted repository.
Prompts for passphrase twice and creates crypto.meta.

7.7 CONFIRMATION BEHAVIOR
==============================================================================
Directory undo without --force asks for confirmation when stdin is a

9. VERSION AND DIFF EXPORT (DUMP)

- Reviewing 10, 100, or more consecutive diffs.

10.3 VALGRIND / SANITIZER POLICY (V1.4)
==============================================================================
WARNING: Due to hardware and time constraints, Valgrind instrumentation is
DISABLED by default for encrypted test sections 39 and 40 when running the
test battery under Valgrind.

Reason:
- PBKDF2-HMAC-BLAKE2b with 100000 iterations is extremely slow under
Valgrind (10-20x slower than native execution).
- XChaCha20-Poly1305 AEAD and dedup block encryption multiply the cost.
- Target development hardware (Core 2 Duo / mechanical HDD) cannot
complete these sections in a reasonable time under Valgrind.

What IS tested under Valgrind:
- Sections 1-38: core functionality, dedup, GC, compaction.
- Section 41: dedicated Valgrind memory audit (leaks, errors).

What is NOT tested under Valgrind by default:
- Section 40: Encryption extended hardening (functional).
These sections ARE fully tested in the normal (non-Valgrind) battery run.

Additional sanitizer policy:
- TSan builds automatically skip section 41.
- ASan/UBSan builds must not be executed inside Valgrind.
- TSan builds must not be executed inside Valgrind.
- ASan and TSan must not be combined in the same build.

If you want to enable encrypted sections under Valgrind:
1. Set SKIP_CRYPTO_UNDER_VALGRIND=0 in mega_test.sh
2. Increase crypto timeouts: CRYPTO_TIMEOUT=600

WARNING: Enabling these sections may increase total test time from
~15 minutes to several hours on the target hardware.

11. DESIGN DECISIONS
==============================================================================
Baseline manifest (v1.4):
undo dir --initial restores the directory to its exact state at the moment
the repo was first adopted. A baseline.list file records which files existed
at that point. Files added afterwards are deleted during --initial restore.

The manifest is written once on first adoption and never overwritten,
preserving the original capture point across daemon restarts.

Multi-repo monolith (v1.3):
A single daemon owns up to 16 repositories. This avoids a process per
folder, keeps one shared inotify instance and one timer, and lets the user
attach/detach folders on the fly. Each repo is still fully autonomous: its
own .timetravel store, cache, and debounce queue. The monolith is an
orchestration layer, not a coupling layer.

Boot lock + IPC discovery (v1.3):
Concurrent `start`/`add` must never create two daemons. The winner of a
flock boot lock becomes the daemon and publishes its IPC socket; every other
invocation discovers it and joins as a client. The lock acquisition is
bounded (~30 s) so a client can never hang forever, and the daemon releases
the lock as soon as it is discoverable.

Hot add/remove over a Unix socket (v1.3):
Repositories are attached and detached at runtime through
.timetravel/timetravel.ipc. A per-user registry under /tmp/timetravel-<uid>/
stores the socket path, pid, and a global status snapshot so any CLI
instance can locate the monolith regardless of the current directory.

Signal handlers live only in the daemon (v1.3):
Client processes (start/add/stop) keep default signal dispositions so that
external timeouts (e.g. `timeout` in the test battery) can terminate a stuck
client with SIGTERM. Only the long-lived daemon installs a handler.

No initial snapshot:
Files are cached in memory on startup but NOT written to disk. Records are
only created on the first change (copy-on-first-change). Original content
is backdated to daemon startup so undo --tag/--to works for pre-existing
files. This avoids writing thousands of records on startup for repos that
might never change.

Atomic restorations:
All writes use mkstemp + write + fsync + chmod + rename. The daemon never
sees a half-written file during restoration. Corruption window: zero, even
under power loss.

Stability verification:
Double-stat (size + mtime in nanoseconds) before recording prevents
capturing files during concurrent writes. Unstable reads are re-enqueued
via debounce for retry on the next tick.

Per-file directory undo:
undo dir --last restores each file to its own previous version, not to a
single global timestamp. This matches the user expectation of "undo my last
changes" rather than "revert to a specific moment".

No fsync per record:
Records are visible via page cache instantly. Durability is bounded by file
rotation and close. Massive performance gain in bursts (500 files in <2
seconds vs minutes with fsync per record).

Manual-only compaction (v1.3):
The automatic 03:00 compaction was removed to keep the daemon's behavior
deterministic and to avoid surprising rewrites during long sessions. Delta
chains are still collapsed on demand with `timetravel compact`.

Robust exclusions:
Directory exclusions (.git, node_modules, etc.) use component matching at
any depth via path_has_component(), not fnmatch with FNM_PATHNAME which
fails on deep absolute paths. File patterns are compared only against the
base name.

Daemon lifecycle via PID file + global registry:
PID + startup timestamp stored in .timetravel/timetravel.pid, plus a
per-user global registry for cross-directory discovery. A second start in
the same repo detects the active daemon and exits cleanly. Stop sends
SIGTERM, waits 5 seconds, escalates to SIGKILL.

Session resumption:
When restarting the daemon over the same repository, it attempts to continue
the last valid .ttd. This avoids unnecessarily fragmenting history into
multiple small files. If the last .ttd is corrupt, locked, or exceeds 64 MB,
a new one is created.

Export vs undo:
undo restores files in the working tree.
dump exports reconstructed versions outside the working tree.
dump is a read-only operation on history and modifies neither the watched
repo nor the store.

13. POSSIBLE ISSUES
==============================================================================
Daemon won't start:
Verify musl-gcc is installed: which musl-gcc
On Debian/Ubuntu: sudo apt install musl-tools
Check that third_party/xdelta/xdelta3/xdelta3.c exists.

`add` says the repo overlaps another:
You are trying to watch a folder that is inside an already-watched
folder, or that contains one. This is rejected by design to avoid
double-capturing the same files. Remove the conflicting repo first
(stop --repo <dir>) or choose a non-overlapping path.

`status` shows no repos:
Either no monolith is running, or a leftover global registry from a
previous run is stale. Run `timetravel start <dir>` to launch one. If
you suspect orphan daemons, kill them and clear /tmp/timetravel-<uid>/.

undo doesn't restore the expected version:
For files that existed before daemon startup, original content is only
recorded on the FIRST change. If no change has occurred since startup,
there is no record to restore from.
Solution: make any edit to the file, then undo will work.

undo dir hangs waiting for confirmation:
This happens when stdin is a terminal and --force is not used.
Press 'y' + Enter to continue, or 'n' + Enter / Ctrl+C to cancel.

In scripts, use a pipe:
echo "y" | timetravel undo dir --last ...
Or use --force to skip confirmation entirely.
diff shows "(no differences)" unexpectedly:

There are three normal causes:
1. The file only has one record (first capture).
2. The selected version is identical to the current file.
3. You are using --to N expecting to see the change introduced by N.
Case 3 is the most confusing.

Example:
timetravel diff src/main.c --repo src --to 15
This compares revision 15 against the current file, NOT revision 14
against revision 15.

To see the change introduced by revision 15, use dump:
timetravel dump src/main.c --repo src --out /tmp/tt_main --with-diff
less /tmp/tt_main/diffs/src main.c/000014_to_000015.diff

Large files aren't captured:
Files exceeding TT_MAX_CAPTURE_SIZE (64 MB) are silently ignored. A
warning is logged in the daemon log. This limit exists to prevent
excessive memory usage during capture and restoration.

.git files appear in history:
This shouldn't happen. The exclusion filter uses component matching at
any depth. If it does, verify tt_filter.c is compiled and linked (check
that compile.sh includes src/tt_filter.c).

Store grows indefinitely:
Compaction is MANUAL in v1.3:
timetravel compact --repo /path/to/project
Compaction collapses delta chains longer than TT_COMPACT_THRESHOLD.

I want to see many diffs, not just one:
Use dump:
timetravel dump <path> --repo <repo> --out /tmp/tt_dump --with-diff
Then:
find /tmp/tt_dump/diffs -name '*.diff' | sort | less
or:
find /tmp/tt_dump/diffs -name '*.diff' | sort | tail -n 100 | less

Encrypted repository won't unlock:
Verify that you are using the correct passphrase and that
.timetravel/crypto.meta exists and is not corrupted.
Without crypto.meta, the repository cannot be unlocked.
I forgot the passphrase:
The passphrase cannot be recovered.
The encryption key is derived from it and is not stored.

compact asks for passphrase:
This is expected for encrypted repositories.
If the passphrase is wrong, compact should fail and dedup GC
should not delete blocks.

verify fails:
verify returns non-zero when the store is corrupted or when
encrypted records fail authentication.
This can happen after manual modification of .ttd files,
disk corruption, or using the wrong passphrase.

blocks/ directory grows:
The blocks directory stores deduplicated content.
Blocks referenced by any historical record are preserved.
Orphan blocks are removed by compact/GC.

Large files take longer to capture:
Files >= 1 MiB are split into 64 KiB blocks, hashed with BLAKE2b
and stored in the dedup pool. This is expected.

Valgrind is killed when running a TSan binary:
This is expected. ThreadSanitizer and Valgrind cannot be combined.
mega_test detects TSan builds and skips the Valgrind memory audit section.

If you need Valgrind results, run it against a native or Valgrind-compatible
binary, not against build_tsan/timetravel.
TSan does not create log files:
ThreadSanitizer usually creates log_path.<pid> files only when it has
something to report.

If you used:
TSAN_OPTIONS="...:log_path=/path/to/tsan.log"
and there are no files like:
tsan.log.12345
then TSan probably did not detect any warning during that run.
To confirm the binary is instrumented:
nm build_tsan/timetravel | grep -m 5 __tsan
You should see symbols such as:
U __tsan_init
U __tsan_read1
U __tsan_write1
ASan binary fails under Valgrind:

Do not combine AddressSanitizer with Valgrind.
Use the ASan build for ASan/UBSan testing and a native/Valgrind build for
Valgrind memory auditing.

mega_test shows Passed: 116+/116+ and Skipped: 1 under TSan:

This is expected. The 116+ functional assertions are evaluated, and the
Valgrind memory audit section is skipped because TSan is active.

==============================================================================
14. DEDUP BLOCK STORAGE (V1.4)
==============================================================================
When a captured file is at least TT_DEDUP_MIN_SIZE (1 MiB), Time-Travel
splits its content into TT_DEDUP_BLOCK_SIZE blocks (64 KiB).

Each block is hashed with BLAKE2b-256 and stored in the dedup pool:
.timetravel/blocks/<first 2 hex chars>/<remaining hex chars>
The .ttd record for a deduplicated file stores only the ordered list of
32-byte block hashes, not the file content itself.

Properties:
- Identical blocks are stored only once.
- Identical blocks can be shared across files and versions.
- Restore reconstructs the file by reading blocks from the pool.
- Orphan blocks can be removed by compact/GC.
- In encrypted repositories, blocks are encrypted individually.
- dump correctly reconstructs and exports deduplicated files
(TT_EV_CREATE_DEDUP events are supported).

Dedup is especially effective for:
- large files with partially repeated content;
- VM images, disk images, archives;
- large generated files with stable regions.

Dedup is less effective for:
- fully random data;
- already compressed data;
- encrypted data with high entropy.

==============================================================================
15. ENCRYPTION (V1.4)
==============================================================================
Time-Travel v1.4 supports optional per-repository encryption using
XChaCha20-Poly1305 (AEAD).

Creating an encrypted repository:
timetravel start /path/to/project --encrypt
The command prompts for a passphrase twice and creates:
.timetravel/crypto.meta

crypto.meta contains:
- magic identifier;
- random 16-byte salt;
- KDF iteration count;
- key verifier.
The passphrase itself is NEVER stored.

Key derivation:
PBKDF2-HMAC-BLAKE2b(passphrase, salt, iterations) -> 32-byte key
Default iteration count:
TT_KDF_ITERATIONS = 100000 (release)
TT_KDF_ITERATIONS_TEST = 1000 (test)

Encrypted data:
- .ttd record payloads;
- dedup blocks.
Authenticated but not encrypted:
- record headers;
- file paths;
- timestamps;
- stored size metadata.
Therefore, encryption protects content but does not hide file names,
timestamps or repository structure.

Important:
- If the passphrase is lost, the repository cannot be recovered.
- crypto.meta must be preserved. Without it, unlocking is not possible.
- Wrong passphrase is detected via the key verifier.
- Tampered encrypted records fail AEAD authentication.
- Tampered crypto.meta is rejected.

==============================================================================
15.1 SEMANTIC AUTOTAGS (V1.5)
==============================================================================
Time-Travel v1.5 automatically generates semantic tags for every capture
event. These autotags appear in the `log` and `extlog` command output:

MODIFY    +1/-1 lines 3 #max_retries                          worker.c
CREATE    CREATE (176 B) #futex_lock #PTHREAD_MUTEX_INITIALIZER  worker.c

Format:
<EVENT>  <quantity> <range> <tags>  <path>
Quantity:
+A/-R lines    Lines added/removed (or replaced)
EDIT [Lx]      Content modified without changing the line count
Range:
N              Single affected line
N-M            Range of affected lines
Tags:
#identifier    Relevant identifiers extracted ONLY from the changed
lines (maximum 4, sorted by frequency).
Language keywords and common tokens are excluded.

Storage:
Autotags are stored in .timetravel/annotations.enc (AEAD encrypted).
Internal format: timestamp_ns \t path \t summary

Files:
tt_autotag.c       Tag generation (tokenization, ranking)
tt_autotag.h       Public API
tt_annotation.c    Encrypted annotation persistence
tt_annotation.h    Public API

==============================================================================
15.2 METADATA ENCRYPTION (V1.5)
==============================================================================
v1.5 automatically encrypts repository metadata files.
The encryption is TRANSPARENT: the user does not need to do anything.

Encrypted files:
annotations.enc    Per-record autotags (formerly: annotations.tsv)
baseline.enc       Baseline file paths (formerly: baseline.list)
exclude.enc        Exclusion patterns (formerly: exclude.list)

Repository key:
Each repo has a 32-byte key automatically generated in
.timetravel/repo.key (0600 permissions).
This key is used to encrypt/decrypt metadata.
The user NEVER needs to interact with this key.

Encrypted file format:
"TTENC01" || nonce(24) || tag(16) || ciphertext

Algorithm:
XChaCha20-Poly1305 AEAD (same primitive as payload encryption).

Backward compatibility:
If legacy plaintext files exist (annotations.tsv, baseline.list,
exclude.list), they are read directly. New files are always written
encrypted.

Security:
- An attacker with disk access sees only random bytes.
- The repo.key has 0600 permissions (owner only).
- If repo.key is lost, metadata cannot be recovered.
- File content remains protected by payload encryption (v1.4) or
plain deltas.

Functions:
tt_repo_get_key()           Generates/reads the repo key
tt_crypto_encrypt_file()    Encrypts a complete file
tt_crypto_decrypt_file()    Decrypts a complete file

==============================================================================
16. FAQ - FREQUENTLY ASKED QUESTIONS
==============================================================================

==============================================================================
16.1 CAN I USE TIME-TRAVEL ON WINDOWS OR MAC?
==============================================================================
NO. Time-Travel uses Linux kernel-specific interfaces:
- inotify for filesystem events
- timerfd for periodic ticks
- rename() atomicity guarantees (POSIX)
- mkstemp for secure temporary files

There is no portability layer. It is Linux-only by design.

==============================================================================
16.2 DOES IT WORK OVER NFS / SSHFS / NETWORK MOUNTS?
==============================================================================
Partially. inotify DOES NOT work over NFS or SSHFS. The daemon will start
but won't receive events. The periodic rescan (every 10 s) will still
capture changes, but with higher latency.

For network directories, consider running the daemon on the server and
accessing the store remotely, or use a tool designed for network backup
(BareSnap, Restic, Borg).

==============================================================================
16.3 HOW MUCH DISK SPACE DOES THE STORE NEED?
==============================================================================
General rule: the store needs between 0.5x and 1x the size of the unique
data being tracked, depending on change frequency.

Factors:
- Delta encoding: small changes produce small deltas (~20-30 bytes for a
line edit in a 600-byte file).
- Full copies: very small files (<~50 bytes) are always stored as full
CREATE because deltas are larger.
- Compaction: collapses long delta chains into base + super-delta.
- Binary files: photos, videos, compressed archives don't generate good
deltas; each version stores almost the full size.

To check current usage:
timetravel status --repo /path/to/project

==============================================================================
16.4 CAN I BACKUP THE .TIMETRAVEL DIRECTORY?
==============================================================================
YES, but it's not recommended. The .timetravel directory contains all
history. Backing it up creates a circular dependency.

Better approach: backup the SOURCE files with a traditional tool (BareSnap,
rsync, tar). The .timetravel store is a local undo buffer, not a backup.

==============================================================================
16.5 WHAT HAPPENS IF THE DAEMON CRASHES?
==============================================================================
The store is NEVER left in a corrupt state:
- Records are written atomically (all or nothing).
- Without fsync per record, some recent records might be lost on power
loss, but existing records remain intact.
- On restart, the daemon rebuilds its cache from disk and continues.
- The PID file is cleaned on graceful exit; obsolete PIDs are detected via
kill(pid, 0) and overwritten on new startup.

==============================================================================
16.6 CAN TWO DAEMONS WATCH THE SAME DIRECTORY?
==============================================================================
NO. In v1.3 there is only ever ONE daemon (the monolith). A second `start`
or `add` detects the running monolith via the boot lock + IPC discovery and
joins it instead of spawning a duplicate. Concurrent startups are
serialized so exactly one daemon is created. Overlapping repos are rejected.

Use `timetravel stop --repo <dir>` to detach a repo, or plain `stop` to halt
the whole monolith.

==============================================================================
16.7 CAN I WATCH SEVERAL UNRELATED FOLDERS AT ONCE?  (NEW IN V1.3)
==============================================================================
YES. This is the headline feature of v1.3. Start the monolith with one
folder and attach the rest hot:
timetravel start ~/src
timetravel add ~/docs
timetravel add /mnt/data/notes

Each folder keeps its own isolated .timetravel store. Inspect the whole
swarm at any time with plain `timetravel status`.

==============================================================================
16.8 IS THERE ENCRYPTION?
==============================================================================
YES, starting with v1.4.
Time-Travel supports optional repository encryption using
XChaCha20-Poly1305.

Create an encrypted repository with:
timetravel start /path/to/project --encrypt

Encryption protects:
- record payloads;
- dedup blocks.

Encryption does NOT hide:
- file paths;
- timestamps;
- file sizes;
- record metadata.
Those fields are authenticated but remain visible.

IMPORTANT:
- The passphrase is not stored anywhere.
- If you lose the passphrase, the repository cannot be recovered.
- crypto.meta must be preserved.
- Back up crypto.meta together with the repository.

==============================================================================
16.9 CAN I SYNC THE STORE TO ANOTHER MACHINE?
==============================================================================
Not natively. The store is a local undo buffer. For remote backup, use a
dedicated tool (BareSnap with SSH, rsync, rclone).

You CAN rsync the .timetravel directory as a rudimentary sync mechanism, but
concurrent access from two machines is unsupported and will corrupt the store.

==============================================================================
16.10 HOW DO I RESUME A SESSION?
==============================================================================
Simply restart the daemon over the same repository:
timetravel stop --repo /path/to/project
timetravel start /path/to/project

If the last .ttd is valid and hasn't exceeded the limit, the daemon will
continue writing to it. Hot-added repos are re-adopted automatically from
repos.list. To check session state:
timetravel status --repo /path/to/project

==============================================================================
16.11 CAN I SEE 100 DIFFS?
==============================================================================
Yes.
The recommended way is:
timetravel dump <path> --repo <repo> --out /tmp/tt_dump --with-diff

Then:
find /tmp/tt_dump/diffs -name '*.diff' | sort | tail -n 100 | less
The practical limit isn't 100; it depends on available history, file sizes,
and disk space for export.

==============================================================================
16.12 HOW DO I SEE THE CHANGE INTRODUCED BY A SPECIFIC REVISION?
==============================================================================
diff compares a historical revision against the current file, not against
another historical revision. To see the delta introduced by revision N,

use dump instead:
timetravel dump src/main.c --repo src --out /tmp/tt --with-diff
less /tmp/tt/diffs/src main.c/000014_to_000015.diff
This generates all consecutive diffs, so you can inspect any inter-revision
change.

==============================================================================
16.13 CAN I USE EXACT DATES FROM THE LOG?
==============================================================================
YES. `undo --to` accepts exact timestamps in the format
"YYYY-MM-DD HH:MM:SS" as shown in the log output.

Example:
timetravel log src/main.c --repo src
# Output shows: 2026-09-13 00:06:17  CREATE  ...  src/main.c
timetravel undo src/main.c --to "2026-09-13 00:06:17" --repo src

This restores the file to the exact state recorded at that second.

18. RESUMING A SESSION
==============================================================================
Time-Travel automatically resumes the session when you restart the daemon
over the same repository.

To stop and resume:
./build/timetravel stop --repo /path/to/project
./build/timetravel start /path/to/project

Behavior:
- Looks for the last .ttd file inside .timetravel/
- If valid, not corrupt, not locked, and under 64 MB, continues writing to it.
- If missing, corrupt, locked, or over the limit, creates a new .ttd.
- Re-adopts any hot-added repos listed in repos.list (v1.3).

Check session state:
./build/timetravel status --repo /path/to/project

View session files:
ls -l /path/to/project/.timetravel/*.ttd

Important:
There is no specific "session continue" command. The session resumes when
you run "start" again over the same repository.

+ `start` is now monolith-aware: if a monolith is already running, the new
repo is attached to it instead of refusing or duplicating.
+ Selective `stop --repo <dir>`: detach a single repo; the daemon exits only
when the last repo is removed. Plain `stop` halts the whole monolith.
+ IPC hot core (tt_ipc.c): repositories are added/removed at runtime over a
Unix domain socket (.timetravel/timetravel.ipc).
+ Boot lock: concurrent `start`/`add` are serialized via flock with bounded
acquisition (~30 s). Parallel invocations bootstrap exactly ONE daemon -
no duplicates, no hangs.
+ Global discovery & status: a per-user registry (/tmp/timetravel-<uid>/)
exposes the socket path, pid, and a swarm snapshot, so plain `status`
(no --repo) reports the whole monolith from any working directory.
+ Overlap protection: adding a repo that contains or is contained by an
already-watched repo is rejected.
+ Independent root health: deleting one repo's directory marks only that
repo as root_lost; the others keep capturing. It recovers on recreation.
+ Per-repo isolation: a corrupted or deleted store in one repo never affects
the others.
+ Persistence: hot-added repos are recorded in repos.list and re-adopted
automatically on restart.
+ Signal handlers now live only in the daemon, so external timeouts can
terminate a stuck client (SIGTERM).
- REMOVED automatic daily compaction (03:00). Compaction is manual only via
`timetravel compact` (TT_COMPACT_HOUR removed).
+ Regression battery expanded to 77/77 across 35 sections. Sections 28-35
cover the multi-repo monolith (hot add, overlap, root loss/recovery,
persistence, bootstrap, stampede, global status, selective stop).
+ Test battery is now self-cleaning (kills leftover daemons and clears the
global registry on startup and exit) to prevent cross-run pollution.
